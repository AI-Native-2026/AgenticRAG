# v2 06 工具治理与审计

> 本节回答：工具多了以后，怎么管住"谁能调、调没调、调了啥"。

## 6.1 工具失控的三个问题

| 问题 | 场景 | 后果 |
|---|---|---|
| **越权** | member 调了 admin 才该用的工具 | 权限边界失效 |
| **失控** | 某个工具被高频调用，打爆资源 | 资源被单点吃光 |
| **无痕** | 出事了查不到"谁调了什么、传了什么参" | 无法追责、无法复盘 |

## 6.2 注册中心（`agent/registry.py`）——集中治理

```python
class ToolRegistry:
    def register(self, name, fn, roles, rate_limit_per_min=0):
        self._tools[name] = {"fn": fn, "roles": roles, ...}

    def can_call(self, name, role):
        meta = self.get(name)
        return meta is not None and role in meta["roles"]
```

**为什么需要注册中心而不是直接 `FunctionTool.from_defaults(fn)`**：
工具一多，权限/限流/审计散落在各个 `__init__` 里就无法管理。
注册中心把每个工具的**能力 + 权限 + 治理**集中在一张表里，
新增工具 = 注册一行（生产上还要加"审批流"）。

**为什么用全局单例**：一个进程只有一个注册中心，所有工具都登记在它名下，
`can_call` 才有意义（否则各自为政）。

## 6.3 鉴权 + 审计包装（`agent/tools.py`）

```python
def _wrap(self, name, fn, allowed_roles):
    def wrapped(*args, **kwargs):
        role = _CTX.role        # 从线程本地取"当前请求角色"
        if not self.registry.can_call(name, role):
            self._log_audit(name, request_id, role, args, kwargs, allowed=False)
            raise PermissionError(f"角色 {role} 无权调用工具 {name}")
        t0 = time.time()
        try:
            result = fn(*args, **kwargs)
        finally:
            self._log_audit(..., allowed=True, ok=ok, duration_ms=...)
        return result
    self.registry.register(name, fn, roles=allowed_roles)
    return wrapped
```

**为什么用线程本地（`RequestContext`）而不是把 role 当参数传**：
FunctionTool 的参数来自 LLM 的 tool_calls，**LLM 不会也没义务传 role**。
API 层在跑 Agent 前 `set_ctx(role, request_id, tenant)`，
工具执行时从线程本地读取——线程安全、无需每请求重建工具。

**为什么"拒绝也要审计"**：越权尝试是安全事件，必须留痕。
`allowed=False` 的记录正是排查攻击的最直接证据。

## 6.4 审计日志（`storage/audit.py`）——不可变留痕

```python
class AuditLog:
    def record(self, tool, request_id, role, args, allowed, ok, duration_ms):
        self.col.insert_one({...})   # 只 append，不改不删
    def query(self, request_id=None, tool=None, limit=50):
        ...
```

**为什么审计和观测事件是两套**：

| | 观测事件（observability） | 审计日志（audit） |
|---|---|---|
| 目的 | 性能/成本 | 合规/追责 |
| 可丢弃？ | 可（丢了影响报表） | **不可** |
| 查询方式 | 文件聚合 | Mongo 带索引查询 |

Mongo 带索引（ts/request_id/tool）是为了合规查询：
"某用户某天调了哪些工具"一条聚合查询就出结果。

## 6.5 权限设计：角色 → 工具集

v2 只有 `member` / `admin` 两档，但设计成**角色矩阵**：
```python
{"kb_search": ["member", "admin"], "calculator": ["member", "admin"],
 "admin_only_tool": ["admin"]}
```
生产演进方向：RBAC（角色→权限表）、ABAC（属性→规则），
甚至**按租户授予不同工具集**（金融租户不给某些工具）。

## 6.7 思考题

❓ 问题：为什么"拒绝调用"也要写审计？不写会漏掉什么？
💡 为什么这么问：安全日志的原则是"异常与正常同样重要"。
🔍 参考思路：越权尝试是攻击信号，不记录就发现不了"有人一直在试"；
   合规审计也要求"所有访问留痕"，包括被拒的。

❓ 问题：如果工具参数里有用户隐私（比如查询内容），审计该不该存参数全文？
💡 为什么这么问：审计本身也可能成为数据泄露源。
🔍 参考思路：要权衡——全文便于追责，但会存敏感数据。生产做法：
   存参数摘要 + 按需展开（引用原始请求，不复制全文），或对敏感字段脱敏。

❓ 问题：角色矩阵 vs 让工具自己在函数体里判断权限，区别是什么？
💡 为什么这么问：治理要"统一执行"而不是"各写各的"。
🔍 参考思路：函数体自判是散的（新增工具容易忘）、无法批量查看；
   注册中心集中声明角色，新增/审查/审计都在这一个地方，权限一目了然。
