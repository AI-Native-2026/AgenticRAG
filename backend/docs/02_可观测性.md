# v2 02 可观测性

> 本节回答：系统跑起来之后，怎么知道它"好不好、慢在哪、钱花哪了"。

## 2.1 为什么需要可观测性（三问）

1. **延迟**：用户说"回答慢"，慢在检索还是 LLM？没有分环节计时就是猜。
2. **成本**：月底账单高，是哪个租户、哪类请求烧的钱？
3. **故障**：某条回答错了/超时，是哪一步出了问题？需要能回放。

## 2.2 核心思想：事件（Event）而不是日志

| | 日志 | 事件 |
|---|---|---|
| 谁看 | 人（排查时 grep） | 机器（聚合脚本算指标） |
| 结构 | 自由文本 | **固定 schema** |
| 用途 | "发生了什么" | "发生了什么 + 花了多久 + 用了多少" |

一次请求会产出一条事件链（用 `request_id` 串起来）：

```
request_start ──┬─ retrieval(耗时) ─┬─ tool_call(工具/参数/耗时)
                ├─ rerank(耗时)     ├─ generate(prompt/completion tokens)
                └─ request_end      └─ ingest_doc(消费端)
```

`make_event` 用**白名单**约束事件类型，防止随手写错字段把 schema 搞乱：

```python
EVENT_TYPES = {"request_start", "retrieval", "rerank", "generate",
               "tool_call", "request_end", "ingest_doc", "quota_denied"}
```

## 2.3 落盘：JSONL Sink（为什么按天分片）

```python
class JsonlEventSink:
    def _day(self): return time.strftime("%Y%m%d")
    def record(self, evt):
        with self._lock:   # 多线程并发写必须加锁，否则两行写在一起
            handle.write(to_json(evt) + "\n")
```

**为什么 JSONL（JSON Lines）**：每行一个 JSON，文件本身就是"可 grep 的数据库"。
**为什么按天分片**：
- 文件无限增长 → 按天切，方便归档/清理
- "聚合最近 24h" 退化成"只扫今天的文件" → 快
- 每个进程一个句柄（`get_sink()` 全局单例），避免反复开文件

```python
    # 按租户累计 prompt/completion tokens → 成本报表
    # 语义缓存命中/未命中 → 命中率
    # tool_call 计数 → 工具使用情况
```

**为什么算 p50/p95 而不是平均**：
平均会被极端值拉高（一个 60s 的超时把平均抬到 20s），看不出"大多数用户
的真实体验"。p95 表示"95% 的请求比这个快"，更接近真实。两个都看：p50 是
典型值，p95 是"最差的 5%"。

**踩坑**：`statistics.quantiles` 要求至少 2 个数据点，只有 1 个样本时会抛
`must have at least two data points`——`_pct` 加了对单样本的兜底。

## 2.5 告警：alerts.py（规则文件 + 检查脚本）

规则存在 `data/alerts_rules.json`（指标/操作符/阈值/提示语）：

```json
{"name": "generate_too_slow", "metric": "latency_p95.generate",
 "op": "gt", "threshold": 15000, "message": "生成 p95 延迟超过 15 秒..."}
```

`check(metrics, rules)` 用 `_resolve` 按 `a.b.c` 路径取值再比较：

```python
def _resolve(metrics, dotted_key):
    for part in dotted_key.split("."):
        cur = cur.get(part)   # latency_p95.generate → metrics["latency_p95"]["generate"]
```

**为什么"规则文件 + 检查脚本"而不是监控平台**：
单机教学场景，一个脚本就够了——它读指标 → 逐条规则判断 → 命中则打印。
原理与 Prometheus + Alertmanager 完全一致（指标 + 规则 + 触发），
上生产时把"检查脚本"换成"Prometheus 规则"即可，心智模型相同。

## 2.6 脱敏（为什么日志里不能出现 key）

```python
_SENSITIVE_KEYS = ("api_key", "key", "token", "password", "secret", "authorization")

def mask(value, key=""):
    if key.lower() in _SENSITIVE_KEYS and isinstance(value, str) and len(value) > 3:
        return value[:3] + "***"   # sk-abc*** 而不是 sk-abcdef123456
```

**为什么必须脱敏**：日志会被采集、聚合、归档，一旦 key 进了日志，
等于把密钥写进了"任何人可查"的地方。v2 没有 Vault（资源限制），
**脱敏就是没有密钥管理的底线**。

```
  rerank       p50= 117.0  p95= 150.1     # 重排毫秒级
  generate     p50=13757.1 p95=16386.3    # LLM 生成是最大头（符合预期）
```

> 观察点：generate 的 p95 远超 retrieval/rerank——这是正常的，LLM 网络
> 生成就是最慢环节。**可观测性的价值就是让你"确认慢在哪"，而不是猜。**

## 2.8 思考题

❓ 问题：为什么"事件类型白名单"能防止 schema 腐烂？自由字段会带来什么后果？
💡 为什么这么问：观测系统的命门是"数据结构稳定"，一旦各写各的，聚合脚本没法算。
🔍 参考思路：白名单强制所有人用同一套事件类型；自由字段会导致聚合脚本里
   一堆 `if "a" in evt` 的兼容判断，最终不可维护。

❓ 问题：p95 和 p50 差距大说明什么？什么场景下 p99 更值得看？
💡 为什么这么问：延迟分布是系统健康的核心信号。
🔍 参考思路：差距大说明存在明显慢尾（可能是超时重试/大请求）；p99 反映
   最极端用户，SLA 承诺 p99 时必看。

❓ 问题：语义缓存命中率 0% 是好是坏？什么时候这个指标"报警"才是真问题？
💡 为什么这么问：新系统命中率天然低，阈值设置要贴合业务。
🔍 参考思路：刚上线没流量/问题高度重复时命中率才会高；阈值过低会误报，
   过高会漏报，告警阈值本身也需要随数据迭代。
