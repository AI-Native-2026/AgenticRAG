# v2 03 消息队列（Kafka）

> 本节回答：为什么文档入库要走队列、Kafka 怎么搭、幂等/死信/优雅停机怎么做。

## 3.1 为什么入库要异步队列化

v1 的流水线是"文档来 → 同步切分/embedding/写库"。两个问题：
1. **阻塞在线**：一次大文档批量导入，embedding 卡几十分钟，Agent 服务被拖死
2. **不可重试**：中途失败只能重跑全部，还可能在半路状态上叠加

队列化后：**生产方只管发消息，消费方（embedding/写库）独立跑**。
高峰削峰、失败重试、扩展消费者都成为可能。

## 3.2 为什么选 Kafka（以及单机怎么装）

Kafka 是"分布式提交日志"：消息落盘、按 key 分区、消费者组并行消费。
v2 环境资源有限，用 **KRaft 单节点**（免 Zookeeper，Kafka 3.x+ 支持）：
- `process.roles=broker,controller`（单节点同时当 broker 和 controller）
- `log.dirs` 指到数据盘（Kafka 日志很大，绝不能放系统盘）
- `KAFKA_HEAP_OPTS="-Xmx512m"`（JVM 堆上限，防吃光内存）

```
# 装 Java（Kafka broker 是 JVM 应用，必须先有 JVM）
apt install -y openjdk-17-jre-headless
# 下载 Kafka（清华镜像）→ /root/autodl-tmp/kafka
# 格式化 KRaft 存储 + 启动 + 建 topic
bin/kafka-storage.sh format --standalone -t $(bin/kafka-storage.sh random-uuid) -c config/server.properties
nohup bin/kafka-server-start.sh config/server.properties > kafka.log 2>&1 &
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic doc_ingest --partitions 3 --replication-factor 1
```

**为什么 3 个 partition**：分区数 = 消费者并行度上限。单机教学 3 个足够，
以后要多消费者并行就靠分区。

## 3.3 抽象层：为什么包一层接口（`queue/base.py`）

```python
class Producer(ABC):
    def produce(self, topic, key, value): ...
    def flush(self): ...

class Consumer(ABC):
    def poll(self, timeout_ms=1000): ...
    def commit(self, messages): ...
    def close(self): ...
```

**为什么抽象**：Kafka 是 JVM 重组件，没装 broker 的机器上没法联调。
抽象出接口后，`dev_backend.py` 用内存队列实现同一接口——
**本地无 Kafka 也能跑通全流程**，切生产只改一个环境变量 `QUEUE_BACKEND`。

## 3.4 生产者（`ingestion/producer.py`）

```python
self.producer.produce(topic=self.topic, key=doc["tenant"], value={...})
```

**为什么 key 用 tenant**：Kafka 相同 key 的消息进同一分区，分区内保序。
同一租户的文档按顺序处理（比如"同一文档先删后加"不串），跨租户可并行。

消息体里带 `request_id`——**链路追踪跨进程贯通**（API 提交时生成，
消费端处理时复用，观测事件能串起来）。

## 3.5 消费者：三个生产级要点（`ingestion/consumer.py`）

### 3.5.1 幂等消费（at-least-once 的兜底）

```python
action, version = self.dedup.decide(ref_doc_id, self._text_hash(text))
if value.get("version", -1) >= 0 and value["version"] < version:
    return   # 过期消息直接丢弃
```

**为什么 Kafka 会重复投递**：
消费端"处理成功才 commit"，但如果处理成功、commit 前进程崩了，
重启后会**重新投递**这条消息 → 处理两遍。
**为什么用版本号裁判**：Kafka 无法保证"恰好一次"，只能靠消费端幂等。
版本号 = "这件事我已经做到第几版了"，旧版消息一律丢。
（生产另一种做法是"消息去重表"，语义相同。）

### 3.5.2 失败处理与死信（DLQ）

处理失败 → 重试（Kafka 本身支持在 `consumer.commit()` 前反复 poll 同一批）
→ 仍失败 → 进 `doc_ingest_dlq` 死信 topic，等人工/后续处理。
**为什么不能一直卡着**：一条坏消息（比如永远解析失败的文档）会让消费者
永远处理不完这一批，阻塞后续所有消息。DLQ 把"坏消息"隔离出去。

### 3.5.3 优雅停机

```python
signal.signal(signal.SIGTERM, self._handle_signal)  # 收到信号 → self._stop=True
signal.signal(signal.SIGINT, self._handle_signal)
```

**为什么必须处理信号**：进程被 `kill`（默认 SIGTERM）时，如果不处理，
正在处理的批没 commit → 重启后重复消费。优雅停机 = 停拉取 → 处理完
当前批 → commit → 退出，避免无谓的重复工作。

## 3.6 为什么消费者要"抗脏数据"

topic 里可能混入历史脏消息（比如手工往 topic 塞过非 JSON 文本）。
反序列化必须健壮：解析失败返回 None，poll 时跳过——**一条脏消息
绝不能搞崩消费者**（v2 实测踩过：手工冒烟消息让消费者 JSONDecodeError 崩溃）。

## 3.8 思考题

❓ 问题：消费者收到"版本=3"的消息，但 dedup 表已记录版本 4，该处理还是丢弃？用一次消息乱序场景说明。
💡 为什么这么问：幂等消费的难点不是"消息不重复"，而是"乱序/过期消息必须被正确丢弃"。
🔍 参考思路：版本 3 < 4，是旧版本的消息，直接丢弃；否则旧版本会覆盖新版本数据。
   Kafka 只保证分区内有序，跨分区/重放都可能带来乱序，版本号是唯一裁判。

❓ 问题：为什么 commit 必须在"处理成功之后"？如果先 commit 再处理会怎样？
💡 为什么这么问：理解 at-least-once 与 at-most-once 的本质区别。
🔍 参考思路：先 commit 再处理 = at-most-once：处理崩了不会重投，但消息丢了；
   先处理再 commit = at-least-once：可能重复但绝不丢失。检索/入库场景宁可重复也不丢。

❓ 问题：消费者只有 1 个实例、topic 有 3 个分区时，并行度是几？为什么？
💡 为什么这么问：理解 partition 与 consumer 的关系。
🔍 参考思路：消费者组里一个实例会接手组内所有分区（1 个消费者消费 3 分区），
   并行度=消费者数=1；要并行就起更多实例。
