# v2 07 数据治理

> 本节回答：数据在系统里流转，怎么做到"可追、可算、可删"。

## 7.1 数据治理的三个能力

| 能力 | 回答的问题 | 对应模块 |
|---|---|---|
| **血缘** | 这条回答凭什么这么说？引用了哪份文档 | `storage/lineage.py` |
| **计量** | 谁在什么时候烧了多少 token？账单从哪来 | `storage/metering.py` |
| **删除** | 用户/文档要删，数据怎么清干净 | 多存储协同（docstore + 向量 + 缓存） |

## 7.2 血缘（`storage/lineage.py`）

**两类边、两种写入策略**：

```python
# ① doc → node（切分阶段，ingest 时写）
def record_doc_nodes(self, ref_doc_id, node_ids, doc_version):
    self.doc_col.replace_one({"_id": ref_doc_id},
        {"node_ids": node_ids, "doc_version": doc_version, ...}, upsert=True)
    # 整条覆盖：文档更新后旧边自然消失

# ② node → answer（回答阶段，计数）
def record_answer_refs(self, node_ids, answer_id, request_id):
    for nid in set(node_ids):
        self.ans_col.update_one({"_id": nid},
            {"$inc": {"ref_count": 1}, "$set": {"last_answer_id": ...}}, upsert=True)
```

**为什么两种边用不同策略**：
- doc→node：随文档重建，**用 replace 整条覆盖**，旧版本边不残留
- node→answer：回答会无限产生，**只累加计数 + 记最近引用**，不存全部历史
  ——否则"每回答一条存一行"会无限膨胀（v2 限定写入量的做法）

**生产价值**：
- 追责：一条错误回答 → 反查引用了哪份文档 → 定位数据问题
- 维护：`top_referenced()` 找出"最常被引用的文档"——最有价值的内容
  值得重点维护，从没被引用的可能是垃圾数据

## 7.3 计量（`storage/metering.py`）

```python
def record_generate(self, tenant, prompt_tokens, completion_tokens):
    self.col.update_one(
        {"tenant": tenant, "day": self._today()},
        {"$inc": {"prompt_tokens": ..., "completion_tokens": ..., "calls": 1}},
        upsert=True)
```

**为什么按 (tenant, day) 聚合**：报表按"租户 × 天"出账，upsert 累加
天然就是聚合结果，查询不用再跑一次大聚合。

**token 从哪来（关键细节）**：
`response.raw` 可能是 dict，也可能是 OpenAI 的 `ChatCompletion` 对象。
两种都要兼容取值（v2 实测踩过：对象形态下 `.get()` 取不到 → 全部记为 0）：

```python
if isinstance(raw, dict):
    prompt_tokens = raw.get("prompt_tokens", 0)
else:
    usage = getattr(raw, "usage", None)
    prompt_tokens = getattr(usage, "prompt_tokens", 0) or 0
```

## 7.4 删除（多存储协同，全链路清理）

删除一个文档，需要同时清三处（v2 在 `consumer` 的 update 路径已有雏形）：
1. **docstore**：`delete_by_ref_doc(ref_doc_id)` 删全部节点
2. **向量库**：`vector_store.delete_by_ref_doc()` 按 where 删向量
3. **缓存**：`cache.invalidate()` 作废相关检索缓存

**为什么必须三处一起**：只删 docstore 不删向量 → 向量还在，检索照样召回
（幽灵数据）；只删向量不删 docstore → 重建索引时又从 docstore 复活。
**为什么不一步事务**：跨库无法原子，生产用"补偿 + 版本号兜底"——
删完先记状态，失败可重试；版本号保证旧数据不被误用。

## 7.6 思考题

❓ 问题：为什么 node→answer 血缘只记"计数 + 最近引用"而不是每条都存？
💡 为什么这么问：血缘功能无限膨胀是数据治理的经典坑。
🔍 参考思路：全部历史会随问答量无限增长；计数+最近引用已满足
   "谁最常被引、最近被谁引"的核心诉求，全量回放交给审计（已存完整）。

❓ 问题：删除文档时"先删 docstore 再删向量"和反过来，各有什么风险？
💡 为什么这么问：跨存储删除没有事务，顺序决定一致性窗口的性质。
🔍 参考思路：先删 docstore → 向量还在的窗口内检索仍能召回（数据泄露窗口）；
   先删向量 → docstore 还在，重建会把"已删"复活。生产用软删除标记 +
   版本号：标记已删后检索过滤掉，后台异步物理清理，窗口可接受。

❓ 问题：计量如果漏记一次调用，对成本报表影响多大？什么场景下会漏记？
💡 为什么这么问：计量是"钱"的数据源，可靠性决定财务准确性。
🔍 参考思路：漏记导致低估成本（预算设了等于没设）；可能漏记的场景：
   进程崩溃丢响应、超时后不知道是否成功、代码路径没走记录点。
   生产做法：在网关统一记（不依赖业务代码），并做"计数对账"。
